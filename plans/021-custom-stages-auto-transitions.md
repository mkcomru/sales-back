# 021 — Custom Stages & Auto-Transitions

> **Это документ с требованиями**, а не пошаговый план выполнения. Здесь описано *что* нужно сделать и *какие решения приняты*, но не *как* именно писать код. Для конечной реализации потребуется много конкретики — структура моделей, детали API, edge cases — это ответственность разработчика.

## Objective

Реализовать систему кастомных стадий воронки продаж с автоматическими переходами.

## Контекст

Сейчас в системе есть фиксированные стадии (ThreadStage enum). Компании не могут создавать свои стадии и настраивать воронку под свой бизнес-процесс. Прод пустой — миграция существующих данных не требуется.

## Что делаем

**Кастомные стадии:**
- Каждая компания создаёт свои стадии воронки (например: "Новый", "Квалификация", "Предложение", "Сделка")
- При создании компании — дефолтный набор стадий (на усмотрение разработчика)
- Стадия имеет: название, цвет, position (порядок), флаг финальности (is_final), тип результата (WON/LOST для финальных), флаг auto_close
- Order без стадии (`stage=None`) — валидное состояние, не теряем заказы

**Автоматические переходы:**
- У стадии может быть условие перехода (transition_condition)
- Автопереход только вперёд по воронке (не откатывает назад)
- AI не меняет стадии напрямую — только заполняет поля, система проверяет условия
- Архитектура не должна мешать добавлению двустороннего движения в будущем

**Флаг `frozen` на Order:**
- Менеджер может "заморозить" заказ — автопереходы не срабатывают
- Решает конфликт когда менеджер оттащил назад, а система пушит вперёд

**Условие "стадия была пройдена":**
- Оператор `$stage_completed: "stage_id"` — заказ был на этой стадии
- Оператор `$prev_stage_completed: true` — стадия с `position - 1` была пройдена
- Данные берутся из OrderLog (использовать тот же enum, не дублировать)
- Позволяет строгий последовательный порядок или гибкое перепрыгивание

**Когда проверяем условия:**
- При изменении order_fields
- При изменении customer_fields (пересчёт для всех активных заказов клиента)
- При создании заказа (определение начальной стадии)

**Недостающие поля для следующих стадий:**
- Отдельный endpoint — показывает какие поля нужно заполнить для перехода на следующие стадии
- Используется при ручном просмотре заказа

**Начальная стадия:**
- Стадия с условием-fallback (пустое условие или `$any`) — туда попадают новые заказы

**Финальные стадии:**
- Флаг `auto_close` — при переходе заказ автоматически закрывается (closed_at, result)

**Ручное управление:**
- Менеджер может вручную переставить стадию в любой момент

**Удаление стадии:**
- Заказы остаются с `stage=None`
- UI предлагает перенести, но не блокирует

## Решения

**Синтаксис условий:**
- MongoDB-like (`$and`, `$or`, `$gte`, `$exists`, etc.)
- Свой парсер/интерпретатор (позволит добавлять кастомные операторы позже)
- Базовые операции: `$and`, `$or`, `$not`, `$eq`, `$ne`, `$gt`, `$gte`, `$lt`, `$lte`, `$exists`
- Кастомные: `$stage_completed`, `$prev_stage_completed`
- Условия могут ссылаться на `order_fields.*` и `customer_fields.*`

**Валидация условий:**
- При сохранении стадии — валидация синтаксиса условия (парсится ли)
- Ошибка сразу, не в runtime

**Размещение парсера:**
- `apps/backend/src/backend/core/conditions/` — изолированный модуль

**Разрешение конфликтов условий:**
- Приоритет по порядку стадий (`position` field)
- Проверяем от меньшего `position` к большему
- Первая подходящая побеждает
- Поведение детерминированное

**Управление порядком стадий:**
- `PUT /stages/reorder` принимает массив ID в нужном порядке
- Backend присваивает `position = index`
- Никакой магии — что прислали, то и порядок

**История переходов:**
- OrderLog достаточно (есть timestamp для аналитики)

## Структура модулей

**Новый модуль `modules/stages/`:**
- `models.py` — StageTemplate модель
- `schemas.py` — Pydantic схемы
- `repository.py` — работа с БД
- `service.py` — бизнес-логика стадий
- `routers.py` — CRUD endpoints

**`core/conditions/`:**
- Парсер/интерпретатор MongoDB-like условий
- Изолированный модуль без зависимостей на другие модули
- Используется из `stages/` и `orders/`

**Изменения в `modules/orders/`:**
- Логика автопереходов (триггер при изменении order_fields или customer_fields)
- Поле `frozen` на модели Order
- Endpoints для recalculate и requirements

## API Endpoints

**CRUD стадий** → `modules/stages/routers.py`:
- `GET /companies/{id}/stages` — список стадий компании
- `POST /companies/{id}/stages` — создать стадию
- `PATCH /companies/{id}/stages/{id}` — обновить стадию
- `DELETE /companies/{id}/stages/{id}` — удалить стадию
- `PUT /companies/{id}/stages/reorder` — изменить порядок (массив ID)
- `POST /companies/{id}/stages/recalculate` — пересчитать стадии для всех заказов компании

**Order endpoints** → `modules/orders/routers.py`:
- `GET /orders/{id}/stage-requirements` — недостающие поля для следующих стадий
- `POST /orders/{id}/recalculate-stage` — пересчитать стадию для одного заказа
